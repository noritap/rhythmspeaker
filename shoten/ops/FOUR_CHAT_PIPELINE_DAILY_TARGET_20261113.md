# リズムスピーカー商店｜4専用チャット・日次量産ルール v1.0
2026-11-13 / 作業ブランチ上の運用案

## GOAL
4チャットを明確に分け、1チャットの「進めて」1回で担当フェーズの一括処理を最後まで行う。毎商品ごとに質問・報告・作業中断しない。下流工程は上流商品の完了ゲートを必須とし、商品ID・通常URL・状態をGitHubで共通管理する。重複なく進め、処理数と完了数を区別する。

## 1. 商品開拓・文字データ20商品登録チャット
- 起動「進めて」→最新GitHub/上流正本を照合→既存20件バッチの未完了を優先→カテゴリバランス配慮で20件を一括調査・同一性/型番/メーカー仕様・国内Amazon通常URL照合→コピー制作→写真なし(null/[])→商品ID衝突検査→上流正本のレビュー/必要な正式登録→READYへの昇格→GitHub再取得・テスト→20件をまとめて最終報告。
- 「原稿作成だけ」「ID候補だけ」「PR作成だけ」で1商品ごとに止めない。権限と安全ゲートを満たすときは上流商品IDの正式登録まで同一実行に含める。
- 20件は目標。確定情報不足・権限・ツール限界で未達なら保存済/CONTENT_READY/READY/未完了を分け、未完了を次バッチへ引継ぐ。数合わせの虚偽登録を禁止。
- 完了判定: READY_FOR_AFFILIATE_LINK（写真任意、メーカー検品、原稿、カテゴリ、正式ID、Amazon通常URL、GitHub保存検証完了）。既存アフィリンク受領済は再取得不要。
- 他チャットの写真・アフィリンク・本番公開を待たない。

## 2. 写真登録チャット
- 起動「進めて」→登録済み画像不足商品を優先→利用権のある本人写真/メーカー許諾素材/Amazon認可API画像を照合→商品型番・色一致→アップロードと表示検証→画像状態台帳更新。
- 画像権利・利用可能なファイル/APIがない商品はHOLDして次へ。写真がないだけで1のREADYを取り消さない。無断転載・AIの偽製品写真禁止。
- 1回の数量は対応可能な最大数。素材不足で60件成功を偽らない。

## 3. 正式アフィリエイトリンク登録チャット
- 起動「進めて」→本人提供の正式リンクを一括照合→上流商品IDと正確に紐付け→承認状態を確認→上流台帳へ保存・検証。推測でリンク生成禁止。
- 受領済リンクを再要求しない。本人が未取得のリンクは自動生成不可、入力待ちとして他の商品を先に進める。
- 40件は当日の受領済/取得済正式URL数が前提。リンク受付だけで公開を代行しない。

## 4. 本番統合・公開チャット
- 起動「進めて」→公開承認・安全・正式リンク・画像の許諾と表示規約・PR/CI/レスポンシブ→公式HP main統合→GitHub Pages確認→実商品/CTA/広告/スマホQA→公開数を記録。
- 20件の公開は前工程の20件が公開ゲートを全通過した場合のみ。PRだけでPUBLISHEDにしない。
- 選択肢: 画像未整備でもテキスト中心表示が公開ゲートに適合するなら公開検討可。別の公開担当が最終判断。

## 共通の計測・引継ぎ
product_idを主キーにし、正式ID未定は候補キー。GitHub上で登録済・原稿完成・READY・画像登録・リンク登録・本番公開を別ステータスとして重複計上しない。1商品が同時に複数のフェーズに存在しても件数は重複して水増ししない。変更時は最新版再読取と衝突防止、テスト、コミット/PR/公開状況を区別。サイトmain/本番への変更はチャット4だけ。External upstream source dataはチャット1と3で必要な権限内の安全な登録を認める。

## 2026-11-13 実測からの工程最適化 v1.1（①商品開拓専用）
**適用範囲**：商品準備と上流正本の登録のみ。公式HP main / catalog.json / 購入CTA / 本番公開は変更しない。

### ボトルネックと理由
- 既存バッチ20件のうち、初期READYは2件。追加の原稿完成はREADY数を増やさない。
- 上流 `data/products.json` は12件（RS-P0016含む）。上流 `publication_state: CANDIDATE` と当チャットの `READY_FOR_AFFILIATE_LINK` は別ステータスなので混同しない。
- 正式サイトの `shoten/editorial.js` は home / sound / outdoor の3ルートカテゴリで、food/apparel/workは案のみ。上流 `category_ids`（life/audio/work等）と公開用3カテゴリも別系統。
- 公開用 `shoten/data-adapter.js` / `tools/validate_shoten_product_ops.py` は正式アフィリエイトリンク、追跡ID、サブカテゴリを要求。①商品準備段階の商品にこの公開ゲートをそのまま適用すると、③本人発行リンク前なので原理的にPASSできない。

### ①専用の先行ゲート（公開ゲートとの分離）
G0 上流main・既存ID・候補キー・既存本人発行リンクを照合。購入済み/関心商品を重複発掘しない。
G1 型番・カラー・容量・セット内容をメーカー公式で特定。一次根拠がない商品はIDENTITY_REVIEWへ。
G2 同一バリエーションの通常Amazon URLを確認。優先証拠はメーカー公式の「Amazonで購入」リンク／既存上流の確認済みURL／本人が出した正規リンクの照合。検索結果や推定コードのみではURL確定扱いにしない。Amazonでの最新在庫までは主張しない。
G3 商品説明・メーカー仕様・比較/制約・本人使用主張の出所・既存正式カテゴリへの対応案を一括制作。
G4 20件のうちG1-G3合格品のみ上流正本へ一括登録。正式IDと識別情報の重複を検査し、既存レコード非破壊を確認。PRはまとめ、権限と安全条件を満たす場合にmain統合、再取得確認。
G5 ①専用候補検証：ID・SKU同一性・一次出典・通常URL・紹介文・画像null・上流データ形式の整合。正式カテゴリへの対応が不明ならカテゴリ保留にする。\
**このG5は公開用catalog validatorの代替PASSを意味しない。** ③リンク登録後に公開用バリデータ/描画/CTA検証を④で実施。
G6 `READY_FOR_AFFILIATE_LINK` は①の必須項目がすべて確認された場合のみ計上。本人発行済リンクがあれば③へ即引継ぎ。通常URLや正式IDが欠ける商品は絶対に計上しない。

### 20商品一括処理の配分
- 優先順：既存20件の未完了→本人指定→カテゴリ不足→季節商品。20商品を1件ずつコミットしない。
- G1とG2を優先。1商品で根拠不足なら理由を記録し、次の候補を進める。原稿を先に長文量産してURL待ちを増やさない。
- 新規20件の不足を埋めるときは、通常Amazon URLの一次証拠がある製品から採用。
- バッチ完了時は `対象20/今回G1-G3完成/上流新規登録/今回新規READY/保留` を**別々**に報告。既存READYを新規成果に加算しない。
- 監査証拠：ブランチ・main SHA、PR、検証実施/未実施、各商品残ゲートを記録。検証未実施ならPASSとしない。

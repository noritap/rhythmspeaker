# リズムスピーカー商店｜商品×ブログ連携・継続更新ルール v1.0
基準日: 2026-11-18 / Source: noritap/rhythmspeaker main

## ゴール
公開済みのはてな記事が「読みもの」に自動で蓄積され、記事と正式掲載済み商品が相互に行き来できる。
**記事公開そのもの**と**商店への新着反映**は別工程。記事未公開を自動公開したと主張しない。

## 正本と境界
- 正式商品: `shoten/catalog.json`。商品の購入リンク、公開承認、画像ルールは既存商品OSが最優先。
- はてな記事: `https://rhythmspeaker.hatenablog.com/` の公開記事が正本。新規執筆・予約投稿は既存Muse/はてなブログ運営ルールで行う。
- 商店内独自記事: `shoten/editorial.js`。商店側固定の選び方記事を維持する。
- 同期表示用の派生スナップショット: `shoten/blog-feed.json`。直接記事本文を複製しない。
- 製品紹介文の事実性、リンク・記事の公開許可は既存ゲートを遵守。ユーザー提供アフィリエイトリンクの転送先再検査はしない。

## 公開後に毎日行う自動作業
1. GitHub Actions `shoten-blog-sync.yml` が12:30 / 18:30 JSTを目安にRSSを取得（GitHubの実行時刻遅延あり）。
2. `tools/sync_shoten_blog.py` が**公開済みの記事のみ**最大40件を解析。正規ドメイン/entry/以外を除外し、URLで重複排除。
3. 記事本文に正式な商店商品URL `https://noritap.github.io/rhythmspeaker/shoten/#/product/RS-P0001` がある場合のみ、商品IDを関連付ける。製品名の曖昧な一致で自動関連付けしない。
4. 変更がある場合だけブログスナップショットをcommitし、GitHub Pagesに反映。記事が0件/取得失敗なら**前回の正常スナップショットを維持**して失敗を記録。
5. 商店は読み込みエラー時も従来の独自記事・商品を表示し続ける。

## 記事制作・連携ルール
- 毎日記事を企画/制作する既存のブログ運営OSを継続。記事は読者の疑問→選び方/用途→向かない条件→該当商品への自然な導線で構成。
- 該当する**公開商品**がある場合、ブログ記事本文に対応する商店商品詳細URLを挿入する。新商品・未公開商品へ偽リンクを置かない。
- 各記事に関連商品を最大3件目安で掲載。まったく関連がない場合は空でよい。
- 商店の商品ページには対応する商店内記事とブログ記事を並列表示。商店の読みもの一覧には新しい公開ブログ記事を先に表示する。
- ブログ記事の最後には「関連商品はリズムスピーカー商店で確認」の内部導線を配置し、ブログ側の改稿ははてな/Muse側の作業として承認フローを守る。
- 投稿ごとの画像重複を避ける。広告表示・実機未使用の正しい表記・商品仕様の出典を守る。

## 運用改善と測定
- 週1回: 公開済み記事件数、新着反映件数、記事から商品への遷移（取得可能時）、Amazon遷移（取得可能時）、リンク切れを点検。
- 0件だった場合はRSS URL・ジョブ失敗・記事の公開状態・GitHub Pages反映の順に確認。RSS未公開の記事は表示しない。
- 記事取得に失敗しても商品公開と購入を止めない。記事・商品マスターの二重管理、新CMS/DB、無用な再調査は行わない。

## 完了条件
A. 既存商店内の記事→対応商品のリンクが使える。
B. 新規ブログ公開後、RSS→snapshot→読みもの一覧へ反映される。
C. ブログ本文に正規商品URLがある記事は商品詳細にも表示される。
D. GitHub Actionsの成功、本番での新着反映・スマホ表示を確認。PRだけは本番完了ではない。

## 2026-11-18 追加｜商店発のオリジナル記事（v1.1）
### 最小公開モデル
- 新しい記事はまず商店 `shoten/editorial.js` の `articles` に公開する。既存SPAの `#/article/<id>` を利用し、新CMSやDBは作らない。
- 記事本文の `lead`, `sections`、タイトル、要約、確認日、対象商品IDを一体で管理。商品IDの対応表は `shoten/data-adapter.js` の `links` に明示する。曖昧な商品名推測は行わない。
- 本文には読者の課題、選び方、対象商品のメリットと不適合条件、メーカー公表値の条件を必ず含める。実測・実使用のないレビュー、根拠のない健康効果、価格・在庫の断定は不可。
- 一記事一主要テーマ。見出しと要約で読む理由がすぐ分かり、3〜5節程度で実用的な判断材料を提供。リンクを増やすより関連性と信頼を優先する。
- `feature:true` はトップの編集枠で優先表示する。ただし複数の記事を重複させない。記事一覧は外部ブログ同期記事も表示する。
- 公開済み商品は既存カタログからのみ取得。商品詳細と記事末尾の関連商品カードを相互リンクさせ、購入CTAは本人提供の既存正式アフィリエイトリンクのみ。記事内にAmazonリンクを重複ハードコードしない。
- 既存のはてなブログ記事を商店内記事として丸写ししない。独自記事を作る場合、類似タイトル・主題の重複を確認する。

### はてなブログへの再利用
- 商店のオリジナル記事が原稿の正本。はてなブログへの転載/リライトは既存Museブログ運営規則・公開承認に従う。
- はてな版では著者・PR表記、公開日、商店記事と関連商品へのリンクを付ける。内容を変える場合、原稿の事実関係と商品IDを維持。
- はてなへの投稿を行っていない場合は「商店公開済み／はてな未投稿」と区別して報告する。ブログ公開後は既存RSS同期により新着として表示されるため、重複カードの発生に注意する。

### 継続編集サイクル
1. 新たに本番登録された商品を優先し、既存記事との重複・需要の高い読者の疑問を選ぶ。
2. 商品カタログの公表仕様・注意点と照合して記事を書く。必要なら一次情報で事実確認。
3. 初期の品質基準は90/100（読者課題25、具体性25、商品整合20、信頼性15、読みやすさ10、導線5）。90点未満は修正。
4. GitHub featureブランチ→既存CI→main統合→本番で記事表示・商品相互リンクを確認。PRを完成と呼ばない。
5. 週次で公開記事数、対象商品の記事カバー率、リンク健全性と取得可能なクリック指標を確認。数値未取得なら推測しない。
6. **記事制作の定期自動実行は別途実行主体・権限が必要**。RSS同期は公開記事の取り込みだけで、新規執筆を自動的には行わない。
